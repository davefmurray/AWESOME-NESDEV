# Agent skills

A skill is a folder with a `SKILL.md` and, optionally, `references/`, `scripts/` and `assets/`. The harness reads only the frontmatter description until the skill is relevant, then loads the body — so a good skill is cheap when idle and specific when invoked.

```markdown
---
name: nes-ppu-bringup
description: Bring up NES PPU rendering from a blank ROM. Use when a built NES ROM shows a black screen, when writing reset/NMI code, or when palette or nametable uploads are suspect.
---

# NES PPU bring-up
...procedure, checks, failure modes...
```

Two fields matter most: `name` (lowercase, hyphens) and `description` (when to use it, written in the words a user would use). Everything else is procedure.

## romdev SKILL.md

**Source:** `http://127.0.0.1:7331/skills/romdev/SKILL.md` (generated from the running server, 426 lines at v0.150.2)

Not a general NES tutorial. It is the operating contract for the MCP:

- **Hard rule:** never install a host compiler or emulator; romdev bundles every one.
- **Session semantics:** one descriptive `x-romdev-session` id for the whole task; 401 without it.
- **Tool reference:** every verb, every operation axis, every parameter.
- **Where the detail lives:** which `platform({op:'doc'})` page to read for the mental model, troubleshooting, toolchains or decomp.

### Install and refresh

```bash
mkdir -p ~/.claude/skills/romdev
curl -s http://127.0.0.1:7331/skills/romdev/SKILL.md > ~/.claude/skills/romdev/SKILL.md
```

Re-fetch after every romdev upgrade. The file is a snapshot; it will not update itself.

### Why it works

The model does not need to discover 38 tools by trial. The skill tells it that `build({output:'run'})` exists, that examples are forkable, and that a compile error is not a reason to `apt install gcc`. That last rule alone prevents a whole class of agent detours.

## Yuki001/nes-skills

**Repo:** <https://github.com/Yuki001/nes-skills> · **License:** none declared · **Last push:** June 2026

Four skills that together cover the NES ROM-hacking loop:

| Skill | Contents |
|---|---|
| `nes-format` | iNES and NES 2.0 headers, mapper table, device IDs for Vs. System / PlayChoice-10, UNIF |
| `6502-assembly` | Instruction set, addressing modes, 16-bit math, multiply/divide, optimization, platform patterns |
| `fceux-lua` | FCEUX Lua recipes: screenshots at frames, CHR/nametable/palette dumps, joypad input, `memory.registerexec` tracing, API discovery. Bundles FCEUX 2.6.6 for Windows |
| `retrodisasm` | Wraps a tracing disassembler: CDL-guided code/data separation, ca65/asm6/nesasm output, `-verify` reassembly, batch mode. Bundles binaries for Windows/macOS/Linux |

### Install

```bash
git clone https://github.com/Yuki001/nes-skills
cp -r nes-skills/skills/* ~/.claude/skills/
```

Project-local: copy to `.agents/skills/` or `.claude/skills/` instead.

### What it is actually good at

- **The format reference is genuinely useful** — header bitfields, mapper numbers, and the "which byte means 4-screen" traps are where agents hallucinate most.
- **FCEUX Lua is a real automation surface.** Buckets of screenshots, CHR dumps, and execution traces without writing a custom emulator harness.
- **CDL is the key idea.** Capture which PRG bytes executed and which were read as data, then feed that to the disassembler so it does not mistake a jump table for code.

### Caveats

- **1★ and no license file.** Read `SKILL.md` before granting tool access; scan the bundled binaries or replace them with your own builds of FCEUX and [retrodisasm](https://github.com/retroenv/retrodisasm).
- The FCEUX bundle is Windows-only; on macOS use Homebrew FCEUX or run the scripts against your own binary.
- The 6502 skill overlaps the standalone `6502-assembly` skill below. Install one, not both, to save context.

## re-skill

**Repo:** <https://github.com/vgrichina/re-skill> · **License:** MIT · **Stars:** ~174

A process skill, not a tool wrapper. Point it at a ROM and it scaffolds a persistent reverse-engineering workspace, then works through a task list.

```bash
mkdir -p ~/.claude/skills
cp -r re-skill/re ~/.claude/skills/re
```

### What it creates

```
REVERSE.md            data-range map, findings, task list, verification checklist
labels.csv            addr,name,comment — loaded by every tool, grows over time
dead_ends.md          stuck log, so the next session does not repeat failures
tools/
  instruction_set.py  CPU opcode database (per platform)
  dis.py              targeted disassembler, auto-loads labels.csv
  search_bytes.py     byte pattern search
  xref.py             cross-reference finder
  decode_tables.py    struct/table decoder
  extract_tiles.py    graphics decoder
  render_screen.py    screen compositor
gfx/                  extracted graphics
web/                  optional faithful reimplementation
docs/                 architecture notes
re_loop.sh            autonomous session driver
```

### Phases

1. Identify — header, platform, CPU, memory map.
2. Decompress — only if packed.
3. Disassemble — build the opcode DB, start annotating.
4. Extract assets — tiles, palettes, tilemaps to PNG.
5. Map data structures — tables, structs, pointer arrays.
6. Validate — cross-check against a running emulator.
7. Web port — optional, plain HTML canvas.

### Autonomous mode

```bash
./re_loop.sh                 # up to 50 sessions
./re_loop.sh --max 10
./re_loop.sh --tasks 3
./re_loop.sh --max-turns 50
./re_loop.sh --dry-run
```

Each session reads `REVERSE.md`, picks the top unchecked task, investigates, updates docs, commits. It stops when no tasks remain or `--max` is reached.

### Caveats

- Deliberately avoids third-party disassemblers, so its analysis is weaker than romdev or Ghidra. Its value is the ledger and the discipline.
- Python 3.8+, `pypng`, `jq` required for the loop script.
- Runs many Claude sessions; watch token spend.

**Pair it with:** `nes-skills` for FCEUX/retrodisasm, or romdev for the disassembly project. Use re-skill for *what to do next*, not *how to decode a mapper*.

## dotnes skills

**Repo:** <https://github.com/jonathanpeppers/dotnes> · **License:** MIT · **Stars:** ~778

[dotnes](https://github.com/jonathanpeppers/dotnes) is a .NET IL-to-6502 transpiler, so its skills are shaped around its own toolchain. Two of the three are useful even if you never write C#.

| Skill | What it does | Portable? |
|---|---|---|
| `nes-decompile` | Decompiles a `.nes` into a C# project, recovering recognizable NESLib calls, strings and `NTADR_A` addresses | Only for dotnes/neslib-style ROMs; commercial ROMs yield mostly comments |
| `nes-rom-debug` | `disasm.py` (iNES-aware 6502 disassembler), `compare_rom.py` (byte + instruction diff), address math, 6502 quick reference | Yes — the scripts work on any iNES ROM |
| `nes-emu-debug` | Runs a ROM in MesenCE and inspects memory/PPU/APU | Yes, with MesenCE |

Install by copying out of the repo:

```bash
git clone https://github.com/jonathanpeppers/dotnes
cp -r dotnes/.github/skills/nes-rom-debug ~/.claude/skills/
cp -r dotnes/.github/skills/nes-decompile ~/.claude/skills/
```

The scripts assume paths inside the dotnes repo; edit them or call `python scripts/disasm.py` from your own project.

## retro-build

**Source:** <https://github.com/jaymcgavren/ai-skills-marketplace> · **License:** MIT

The smallest useful NES plugin: confirms the project is NES, assembles with `ca65`, links with `ld65`, optionally opens the ROM in Mesen.

```text
/plugin marketplace add jaymcgavren/ai-skills-marketplace
/plugin install retro-build@ai-skills-marketplace
/retro-build:nes-build
```

Prerequisites: `brew install cc65`, Mesen at `/Applications/Mesen.app`. macOS-oriented; the commands are easy to adapt elsewhere.

Good companion read: Jay McGavren's walkthrough of generating a first NES ROM with Claude Code — <https://jay.mcgavren.com/2026/05/25/claude-code-for-nes-development.html>.

## MesenCE skills (mesence plugin)

**Repo:** <https://github.com/sadnescity/MesenCE> · **Plugin:** 3.1.1 · **License:** GPL-3.0

The `mesence` plugin bundles 14 skills with the MesenCE MCP server. The ones that matter for NES:

| Skill | What it encodes |
|---|---|
| `mesen-workflows-nes` | NES-specific RE workflow: memory types, address conversion, what to try first |
| `mesen-romhacking` | Cheats, tiles, palettes, Lua, TBL text search, ROM patching |
| `mesen-disassembly` | Disassembly, assembly, labels, CDL, tracing, profiling |
| `mesen-memory` | Read/write, search, freeze, access counters |
| `mesen-debug-execution` | Stepping, breakpoints, callstack, expressions |
| `mesen-console-reference` | Per-console memory/CPU/tile-format reference for 7 systems |

Install via the marketplace (requires MesenCE running with MCP enabled):

```text
/plugin marketplace add sadnescity/claude-plugins
/plugin install mesence@sadnescity-plugins
```

**Why it is the closest to end-to-end:** the workflow skill supplies the procedure, and the MCP supplies memory search, write breakpoints and CDL. That is the loop this wiki describes, packaged. The caveats are real: 0★, one author, a separate emulator fork, and a marketplace entry that used to be a 33-tool `mesen2` plugin. See [MCP servers](mcp-servers.md).

## gearlynx-romhacking

**Source:** <https://github.com/drhelius/Gearlynx/tree/main/skills/gearlynx-romhacking> · **License:** GPL-3.0

Not an NES skill, and not a separate repo — it lives inside the Gearlynx emulator. It is the best-written example of the genre, and worth reading as a template even if you never touch a Lynx.

What it does well:

- **The full loop**: capture a value → change it → search again → write breakpoint → identify the writer → patch.
- **Cheat discovery** from write breakpoints, not guessed addresses.
- **Sprite and text table hunting** with a translation workflow.
- **Save states as checkpoints**, so every experiment is reversible.
- **A hardware reference library** (~15 files) shipped alongside the skill, so the model can look up registers instead of inventing them.
- **Setup guidance** that checks whether the MCP server is already connected before telling you to install anything.

Install (only useful with the Gearlynx MCP server):

```bash
git clone https://github.com/drhelius/Gearlynx
cp -r Gearlynx/skills/gearlynx-romhacking ~/.claude/skills/
```

Read it for structure: description triggers, prerequisite check, phases, verification. Then write the NES version.

## sadnescity/romhacking (translation method)

**Repo:** <https://github.com/sadnescity/romhacking-claude-plugin> · **Version:** 1.0.1 · **License:** MIT

A guided, gated method for **game translation**, game-agnostic. This is the polished workflow skill that the NES pack lacks — it just aims at text rather than mechanics.

```
recon → encoding (table + control codes) → accents → space
→ graphics → glossary → translation → QA → patch
```

- Project state lives in `ROMHACK.md` next to the data.
- Every phase has a gate that is proved, not declared: a table counts when its round-trip is byte-identical; accents count when they are readable on screen.
- `scripts/` are Python 3, standard library only: TBL tables, relative search, pointers, dump/insert, iNES, entropy, tiles/PNG, IPS, project state. Seeds to adapt, not finished tools.
- Orchestrates emulator plugins rather than duplicating them.

Install:

```text
/plugin marketplace add sadnescity/claude-plugins
/plugin install romhacking@sadnescity-plugins
```

**Use when:** you are translating text, menus, or fonts. **Do not use when:** you want infinite lives; that is the memory loop, and this plugin will make you do table work first.

## Game-specific: Tecmo Super Bowl

TSB is its own platform in practice: custom bank map, event engine, pointer tables, 28/32-team variants. The repo keeps a separate category at [`../skills/tecmosuper/`](../skills/tecmosuper/README.md):

| Skill | Use |
|---|---|
| `tecmosuper-events` | The `$C390`/`$C3A2`/`$C3AF` event API, sequence vs scene IDs, and the full event library |
| `tecmosuper-rom-map` | 32 × 8 KB PRG banks, `$C000`/`$E000` fixed banks, CPU↔file offsets |
| `tecmosuper-hacking` | TSBTool `SET` commands, hex edits, rebuilding from the 2025 disassembly, patches |

The key distinction the events skill enforces: a **sequence index** (`CUTSCENE_TO_DRAW` → `CUTSCENE_ADDR`) is not a **scene ID** (the byte inside the sequence). Confusing them is the usual reason a TSB cutscene edit plays the wrong thing.

## The gap, updated

The 2026 picture is better than "scattered pieces":

- **Live NES hacking:** MesenCE + `mesence` gives tools + a NES workflow skill.
- **Translation:** `sadnescity/romhacking` gives a gated method.
- **Static analysis:** `nes-skills` gives FCEUX Lua, CDL and retrodisasm.
- **Project scaffolding:** `re-skill` gives the ledger and autonomous loop.
- **One-shot:** romdev gives the whole loop behind one MCP.

What is still missing is a **free, NES-mechanics-specific** skill that wraps MesenCE's search loop and hands off to retrodisasm for a permanent patch. The closest assembly today is `mesence` + `mesen-workflows-nes` + retrodisasm. That is the skill worth writing.

## Writing your own NES skill

The best skill encodes something you had to learn the hard way. "How to get a black-screen ROM to render" is a better skill than "all about the NES".

### Layout

```
skills/nes-ppu-bringup/
  SKILL.md
  references/
    ppu-registers.md
    palette.md
  scripts/
    check_rom.py
```

### Template

```markdown
---
name: nes-ppu-bringup
description: Diagnose a black-screen NES ROM and get PPU rendering working. Use when a built ROM runs but shows nothing, when writing reset/NMI code, or when palette/nametable uploads are suspect.
---

# NES PPU bring-up

## When to use
A ROM builds and the emulator runs, but the screen is blank or garbage.

## Procedure
1. Confirm the reset vector points at your reset code (`$FFFC`).
2. Disable NMI and rendering before touching PPU registers.
3. Wait for vblank twice after power-on; read `$2002` to clear the latch.
4. Upload palette to `$3F00`, nametable to `$2000`, then set scroll.
5. Enable NMI (`$2000` bit 7) and background rendering (`$2001` bit 3).
6. Run 120+ frames, not 2.

## Checks
- `$2002` bit 7 toggles once per frame (vblank).
- Palette byte 0 is not black-on-black.
- Nametable is not all `$00` with a blank tile 0.

## Failure modes
- Writing PPU data with rendering on: corrupts the address latch.
- Forgetting the second vblank wait: first write is dropped.
- CHR-RAM without uploading tiles: everything is tile 0.

## References
- `references/ppu-registers.md` for the register table.
```

### Rules that keep skills useful

1. **Description triggers on user language**, not jargon only. Include "black screen", "nothing renders", "garbage tiles".
2. **One procedure per skill.** If it needs a flowchart, split it.
3. **Put tables in `references/`**, not the body, so they load only when needed.
4. **Scripts must be runnable and path-relative.** No absolute paths to your machine.
5. **State what you verified and when.** A skill that says "tested on romdev 0.150.2, Oct 2026" is worth ten that do not.
6. **No secrets, no ROMs, no copyrighted assets.**
7. **Add an eval.** A prompt that should trigger it, and one that should not.

### Test it

```text
# should trigger
My NES ROM builds but the screen is black.

# should not trigger
How do I install cc65 on Ubuntu?
```

If the second one triggers, your description is too broad. Tighten it.

## Skill hygiene

- **Read before you install.** A skill can instruct an agent to run shell commands. Treat it like code from a stranger.
- **Pin commits.** `git clone` gives you `main`; record the SHA in your project.
- **Avoid overlapping skills.** Two 6502 references compete for context and can contradict each other.
- **Delete what you do not use.** Idle skills still cost a description in the tool catalog.
